# 基于风格标签的美术作品欣赏智能推荐系统的设计与实现

## 摘要

美术作品目录通常支持按作者、题名或类别检索，但初次访问者可能说不出具体作品名称，只能描述所偏好的风格。针对这一问题，本文设计了一个结合风格标签与行为数据的美术作品欣赏系统。系统采用 Vue 3 和 Element Plus 实现浏览端与管理端，使用 Flask 提供接口，通过 SQLAlchemy 管理 SQLite 开发库和 MySQL 部署目标库。作品使用风格、题材、媒介和年代四类标签，支持作品检索、图像展示、账号管理、偏好设置及点赞、收藏、评分。推荐模块先用显式风格偏好和历史作品标签构建亲和度，再使用物品协同过滤计算作品间相似度，辅以热度、最新作品和编辑置顶。对于访客及缺少历史的用户，系统按信息可用程度选择热门或标签排序；对于明确给出低评分的用户，系统在个人推荐中排除对应作品。功能验证采用受控数据，覆盖发布可见性、状态撤销、推荐策略切换和排序变化。本研究给出可追踪的接口、数据结构和验证条件，为后续使用真实交互数据评估推荐质量提供基础。

关键词：美术作品；风格标签；物品协同过滤；混合推荐；冷启动

## Abstract

Artwork catalogues usually support queries by title, artist or category. Visitors who have a stylistic preference but do not know a specific title need a different way to discover works. This project designs an artwork appreciation system that combines style tags with interaction history. The client uses Vue 3 and Element Plus, while Flask provides the application API. SQLAlchemy supports a SQLite development database and a MySQL deployment target. The system describes artworks with style, subject, medium and period tags, and supports browsing, search, preference settings, likes, favourites, ratings and administrative workflows. The recommender constructs tag affinities from explicit preferences and past interactions, and estimates item similarities from co-occurring user interactions. It also uses popularity and editorial signals and falls back to a popularity or preference ranking when history is unavailable. Controlled integration tests cover visibility, interaction reversal, recommendation fallbacks and ordering. These tests establish functional behaviour under defined inputs. Recommendation quality for actual visitors requires separate evaluation on real interaction data.

Keywords: artwork appreciation; style tags; item-based collaborative filtering; hybrid recommendation; cold start

## 第1章 绪论

### 1.1 研究背景

当作品数量较少时，按时间排列的作品列表可以满足简单浏览。作品数量增加后，用户在相同入口中需要面对更多题材与表现形式，传统搜索则依赖用户能提出明确查询。例如，已知某位画家的姓名时，关键词查询能够缩小结果范围；只知道自己喜欢留白较多、墨色变化明显的作品时，单靠题名却很难形成准确的查询。本课题以人为整理的风格标签作为入口，允许用户从审美描述出发，再逐渐认识作品名称、作者与创作背景。

作品鉴赏与按单一标准排序的任务不同。同一作品可能兼具抽象风格、城市题材和数字媒介，同一风格也可出现在多种题材中。若把这些属性放进一张无类别的列表，用户很难判断筛选结果体现的是画面形式、制作材料还是描述主题。系统采用四个维度，允许一件作品关联多个标签。风格用于偏好设置，题材、媒介和年代用于作品检索，也可随交互历史补充推荐信号。分维度建模使同一个词在不同类别中可以有不同含义，并给管理员提供了检查标注一致性的依据。

只使用标签时，新作品一旦完成标注便可进入推荐，但标签词表难以覆盖所有审美差异，也无法利用观众之间的行为共性。只使用协同过滤时，尚无互动的作品与刚注册用户都缺少可计算的相似关系。本文将两者结合，显式偏好为进入系统后的第一次排序提供依据，累积行为为后续排序提供差异。热门和最新入口服务于还没有明确偏好的人，并可让用户主动比较不同的探索方式。

### 1.2 研究现状与技术选择

Sarwar 等在物品协同过滤研究中从用户与物品的交互矩阵计算物品间关系，并依据历史物品预测用户对候选物品的兴趣[1]。物品关系可以为多个用户复用，且便于给出“与已欣赏作品相近”的解释。本文沿用物品相似度这一基本思想，输入则采用本系统的浏览、点赞、收藏和评分信号。Hu 等指出，隐式反馈的观测值更多表达行为发生以及对偏好的置信程度，未观测记录不能直接理解为不喜欢[2]。因此，本文将浏览设为弱正向信号，仅把明确低评分视为排除依据。

王沛澍和杜淑幸以组合标签连接用户画像与产品画像，说明标签可以在需求与物品信息之间建立可计算的联系[3]。该研究采用组合标签与随机游走，本文选用显式标签亲和度与物品相似度的加权组合，便于逐项复核得分，也便于用小规模数据测试状态变化。工程上保留一个明确的标签词表，并使标签在筛选、偏好和推荐理由三个位置使用同一标识，降低不同模块各自维护含义的成本。

推荐质量通常包含相关性、覆盖率、多样性与新颖性等维度[4]。热门排序可在信号缺失时提供有内容的入口，但会把曝光集中在已有互动较多的项目上，降低长尾作品的可见性[5]。多样化研究也指出，需要先明确希望在何种属性上实现多样，再选择度量和排序策略[6]。对作品欣赏而言，可分别观察风格与题材的分布，并保留最新作品入口。本文实现了混合排序和热门回退，尚未在最终列表中加入专门的多样化重排约束。

评价结果取决于数据切分、候选集和统计口径。若训练阶段可以看到测试阶段才出现的互动，计算得到的物品相似度会包含未来信息。即使平均值较好，也可能掩盖新用户与重度用户之间的差异[7-8]。因此本文将工程功能测试与离线效果评价分开。工程测试使用已知输入验证分支选择、状态变化与结果顺序，离线评价则应在获取可授权使用的真实数据后固定时间切分、基线和指标。当前实验只回答已实现规则是否按预期运行。

### 1.3 研究内容

本文完成三项与作品发现直接相关的工作。第一，建立可维护的作品和标签数据模型，并通过发布状态控制公开可见性。第二，建立从账号与显式偏好到浏览、点赞、收藏、评分的交互链路，区分当前状态和历史事件。第三，建立混合推荐模型，说明行为强度、物品相似度、标签亲和度和排序回退之间的关系，使用受控场景验证输出。

需求和实现按可追踪的版本分别记录。论文以主分支提交 3965c9d 为共享基线，同时参考作品标签提交 19b2de5、用户交互提交 2519fec、推荐提交 83a4f2f 和环境脚本提交 693844e。各提交代表不同模块的实现边界，分支验证不能当作全部功能合并后的验证。第2章分析需求和验收条件，第3章说明系统结构与数据模型，第4章详细给出推荐算法，第5章讨论主要模块的实现，第6章汇报验证和后续评价方案，第7章总结与展望。

## 第2章 需求分析

### 2.1 使用角色

访客可查看公开作品、使用关键词和标签筛选，阅读作品介绍以及使用热门、最新入口。登录后，用户可以保存风格偏好，查看个性化结果并进行点赞、收藏或评分。账号资料、收藏夹和个人偏好仅向该用户开放。管理员使用独立权限管理作品、标签和账号，配置推荐权重，并查看基础统计。任务书的需求分析列出审核员，预期功能明确给出了普通用户与管理员。本项目当前把作品上架和下架归入管理员职责，独立审核员及审核意见流转作为待扩展需求。

角色隔离需要在服务端执行。前端可以隐藏管理入口，服务端仍须在每次管理请求中检查当前会话和角色。身份未建立时返回 401，身份有效但角色不足时返回 403。不存在或对普通用户不可见的作品返回 404，避免列表过滤与详情接口使用不同可见范围。用户状态被管理员停用后，已有会话也应在下次受保护请求中被拒绝。这些条件可通过使用同一路径切换不同身份来验证。

### 2.2 普通用户需求

作品列表应支持题名或作者查询、分类标签和分页。关键词与多个维度可以组合，同一页应使用固定排序规则，避免时间字段相同时结果顺序不稳定。详情页展示原图或高清地址、作者及作品介绍，封面与原图应承担不同用途。列表优先使用体积较小的封面，详情再提供更清晰的图像。作品没有查询结果时应给出空列表；作品被下架后，原详情链接也应停止向访客展示。

用户可注册、登录和维护资料，保存可勾选的风格标签。点赞和收藏需要支持取消，评分限制在 1 至 5 的整数范围。浏览记录以登录用户访问公开详情为主，访客可以浏览，但不会形成可回溯至账号的个人历史。收藏夹应查询当前有效收藏，并再次检查作品公开状态。作品下架后仍可保留历史关系，以便分析和后续运营，普通用户的收藏列表则不应提供该作品入口。

推荐页提供个性化、热门和最新三类结果。个性化应在用户明确改变偏好、撤销收藏或提交低评分后反映当前状态。热门由群体行为和置顶规则共同决定。最新入口依据代码保存的创建时间排序；如果运营需要按审核通过时间或重新上架时间排序，需要单独维护发布时间。本需求以结果可复核、异常输入明确响应为验收条件，不承诺对每一个用户都比纯热门得到更高满意度。

### 2.3 管理员需求

管理员需要能新建草稿，编辑题名、作者信息、作品介绍、图像地址与标签，发布或下架作品。作品没有可用原图时可保留草稿，发布前需要满足图像地址要求。图像上传应检查格式和尺寸，并生成适合列表展示的封面。作品分支限制上传体积、总像素和最长边，降低单个大图占用过多解码资源的风险。对本地上传和外部图像地址分别处理，外部地址的可用性由运营审核确认。

标签维护包括新增、编辑、分类和删除。类别内同名标签需要唯一，避免筛选时出现两个视觉相同但标识不同的选项。删除或改变已用于偏好设置的标签时，应同时处理相关引用，使作品筛选和个人偏好不会残留无效选项。用户管理支持查看账号、启停状态和重置密码。推荐配置应限制权重的合法范围，方便在测试数据集上对比不同组合，也使运维人员能够快速恢复一组已知参数。

### 2.4 非功能需求与验收

系统需要在开发环境可复现：依赖版本可追踪，首次运行能建立空库，已有数据库和配置可重复使用。页面可用性关注键盘输入、查询结果、空状态、错误提示和管理表单的操作反馈。性能需分别考虑作品列表查询、图像加载与推荐计算；对演示规模可使用请求内计算，而真实上线前必须测量不同数据规模和并发条件下的分位延迟。可靠性需要验证跨表更新、重复提交、下架和权限变更等边界。生产部署还需要数据库迁移、备份、HTTPS 和日志保留策略。

### 2.5 标签标注与资源验收

标签的粒度需要服务于用户选择。以一件水彩画为例，“水彩”既可被日常使用者当作视觉印象，也可用于说明材料与技法。在本系统中，管理员应先判断标签希望回答的问题。如果它表达媒介，则归入媒介类别；如果希望同时表达一种相对稳定的视觉形式，应选用明确的风格词，并保留媒介标签。题材如“海岸”回答画了什么，年代回答作品创作或发布的时期。各维度可同时存在，从而支持以风格为主、辅以题材或媒介的组合检索。

作品录入可以采用先查资料、后加标签、再预览的顺序。基本资料包括作者、题名和简要介绍，应与来源信息交叉核对。图像应确认允许用于演示或展示，记录来源与使用许可；对于难以确认作者或权利的作品，可继续保留草稿等待复核。系统具备图像上传和发布检查，现有模型没有专门的授权凭据表。实际运营中可通过外部登记表关联作品标识，待明确数据要求后再将来源、许可类型和凭据管理加入模型。

若希望评价标注质量，可选择一组作品由两名录入者分别使用相同词表标注，再对风格和题材维度核对分歧。对同义标签应确定一个可展示的规范名称，别名可以保留在编辑规范中。对于存在争议的作品允许多个标签并存，同时检查是否混入描述情绪或颜色的临时词。这个过程不需要改变排序代码，却可以减少推荐输入的系统性偏差。

## 第3章 系统总体设计

### 3.1 逻辑架构

系统由浏览器、API 服务和数据层组成。浏览器通过 Vue 路由组织发现页、作品页、账号页和管理页。Element Plus 提供输入框、表格、分页和状态提示组件。前端把网络请求集中到统一客户端，页面只关注参数和结果。服务端在 Flask 蓝图中按资源划分接口，认证、作品、交互、推荐和管理接口共用配置与数据库会话。推荐分支进一步将行为聚合和排序从路由中移入服务模块，使排序逻辑能够独立测试。

[[ARCH]]

请求经过 Vite 代理或部署入口送到 API。使用相对路径使开发与部署的界面代码可以复用，避免页面硬编码后端域名。服务端从会话恢复用户身份，按接口要求决定是否需要登录和是否需要管理员权限。数据库事务以单次业务写入为边界：成功写入后返回当前状态，输入错误由接口返回说明。数据库负责关系型数据，上传文件保存在实例目录，记录内保存图像访问路径。数据库备份和文件备份需要协调，否则恢复后可能出现图像地址存在但文件缺失的情况。

### 3.2 数据模型

用户、作品和标签是三个基础实体。作品与标签通过中间表形成多对多关系，用户和风格偏好也通过中间表关联。相同标签可被不同作品复用，删除一个作品或标签关系时，其他作品仍能保留该标签。收藏、点赞和评分通过用户与作品的组合键表达当前状态。行为日志使用单独标识记录事件，允许同一用户在不同时间对同一作品多次浏览。

表3-1 主要关系表及用途

| 关系表 | 关键约束或连接 | 业务用途 |
| --- | --- | --- |
| users | 用户标识、唯一用户名 | 密码摘要、昵称、角色和启用状态 |
| artworks | 作品标识 | 图像地址、作者介绍、状态和置顶 |
| tags | 名称与类别联合唯一 | 风格、题材、媒介、年代 |
| artwork_tags | 作品标识与标签标识 | 作品多标签关系 |
| user_preferences | 用户标识与标签标识 | 账号选择的风格偏好 |
| likes / favorites / ratings | 用户标识与作品标识 | 记录有效点赞、收藏和当前评分 |
| behavior_logs | 事件标识、用户和作品外键 | 浏览与状态变化日志 |
| recommendation_settings | 配置键 | 推荐权重配置 |

业务状态和事件分别保存有两个理由。首先，点赞与收藏是可撤销的，如果直接用累计行为次数计算分数，取消收藏后仍会看到相关作品被高估。其次，保留事件有助于解释用户当时做了什么，并允许未来使用时间窗口统计热度。当前推荐服务使用浏览日志以及点赞、收藏和评分的有效状态。两个来源虽然属于不同表，但都以用户标识与作品标识连接，可以先聚合浏览次数再形成稀疏行为矩阵。

### 3.3 状态和事务

作品可处于草稿、公开、下架三种状态。作品创建后默认草稿，管理员补齐资源再公开。公开列表、详情、收藏夹和推荐应统一以公开状态作为候选条件。下架操作改变可见性并保留作品记录，恢复发布后可重新进入候选集。是否需要清空过去的互动取决于运营策略；当前保留历史，使对同一作品的关系不会随着临时下架而丢失。

对用户交互，接口使用 PUT 并发送期望状态。客户端发送收藏开启时，服务端检查是否已存在相同关系；若已存在则返回已有状态。发送关闭时只有当前关系存在才删除。评分被重复提交为相同数值时不增加新的状态事件。这些处理可以覆盖常见重试。多个请求真正同时到达时，数据库唯一约束仍是防止重复记录的最后保证。原型使用通用冲突响应，生产环境可以进一步加入基于原子更新的并发控制。

### 3.4 接口契约

接口以 /api 为共同前缀。读取接口返回统一的 JSON 结构，列表包含 items，分页资源还包含总数与页码信息。更新接口根据请求类型接受 JSON 或 multipart 文件表单，返回更新后的记录或状态。HTTP 状态码与消息共同表示异常。前端可在表单旁显示问题，也能按 401 提示登录。图像服务使用独立路径，封面与原图的文件标识由服务端生成。应用健康接口表示进程可响应，可在生产中另设数据库就绪检测。

### 3.5 架构取舍

原型用同一个数据库保存账号、作品和互动关系，便于写出可追踪的查询并进行测试。将图像文件与数据库分离可避免数据库体积随原图迅速增长。开发阶段的 SQLite 便于在不同工作树独立启动；部署目标 MySQL 可使用单独账号和权限管理。SQLAlchemy 提供映射与多数查询的统一写法，仍要验证数据库差异，包括字符排序、约束、事务隔离和时间类型。首次建表命令适用于空库，正式结构演进需要有版本的迁移方案。

推荐服务直接从数据层读取行为和标签，部署简单，行为更新后下一次请求即可影响结果。代价是每次计算都需要聚合和排序，数据库与 CPU 负担随数据增加。模块拆分使后续可以保留同一个接口契约，在服务内部替换为预计算或缓存方式。对于当前小型目录，方案优先解决推荐规则可理解和行为变更可验证的问题。

### 3.6 异常场景与一致性

在作品发布和用户互动同时发生的情况下，请求可能在不同时间读取作品状态。例如，用户打开详情时作品处于公开，点击收藏之前管理员已下架。此时互动接口必须重新检查可见状态，才能避免按照旧页面信息保存新关系。对于已有收藏，列表读取时同样检查公开状态。因为页面显示与数据更新之间存在时间差，前端收到 404 后应提示作品已不可用，不能把它当作可重试的数据库故障。

上传图像和保存作品是两次独立操作。图像上传成功、作品保存失败时，可能留下一个暂未引用的文件。反过来，数据库还原后可能出现记录引用了缺失的文件。原型使用直接写入文件的方式降低部署复杂度，无法让数据库事务同时管理本地文件。可行的扩展是为上传资源设置待绑定状态，记录上传者、创建时间和被引用作品，定期清理经过宽限期仍未绑定的记录。清理前应重新校验引用状态，避免与并行编辑产生冲突。

对会话异常，认证状态和账号启停每次由后端判断，页面中的用户名和导航状态仅用来说明界面当前展示的身份。用户收到未登录响应时可以重新建立会话，禁止访问则需要检查账号角色。对表单业务错误，应保留尚未保存的内容并指出具体字段。对服务不可用，界面应提示稍后重试，同时保留日志关联信息。上述处理把失败原因与可执行的恢复步骤联系起来，也是后续浏览器回归所需的验收场景。

## 第4章 混合推荐算法设计

### 4.1 输入信号和矩阵定义

设 u 表示用户，i 表示作品。算法只考虑公开作品和启用账号。浏览次数记为 V，当前是否点赞记为 L，当前是否收藏记为 F，评分记为 R。L 和 F 为 0 或 1。评分缺失时，评分贡献为 0；评分为 3 时也不增加正向强度。对没有低评分约束的用户作品对，正向行为强度由式（4-1）计算。

（4-1） w(u,i) = 0.2 × min(V,3) + 2 × L + 3 × F + max(R−3,0)

浏览只反映一次接触，可能由误点、重复访问或查阅信息产生，使用低权重并把次数截断为 3。点赞一般是较主动的认可，收藏还表示用户有意保留入口，因此设计上收藏权重高于点赞。高评分作为显式信号增加强度，低评分视为明确的排除信号。评分为 1 或 2 时，对应用户作品对不贡献正向矩阵和热度，作品也不进入该用户的个人结果。该规则有意让明确反馈覆盖浏览或既有收藏，但不改变收藏数据本身，用户仍可通过收藏页维护关系。

例如一名用户浏览某作品 5 次、当前点了赞并给出 4 分，没有收藏，则浏览贡献为 0.6，总强度为 3.6。若其随后收藏，该值变为 6.6；取消收藏后回到 3.6。相似度估计时将每个强度截断到 5，目标用户对候选作品预测时仍使用原强度。这种区分允许个体的收藏和评分影响自己的排序，同时避免某一个用户的高强度组合过分影响全局相似度。

聚合后的矩阵按用户保存非零记录。用户未浏览或未反馈的作品没有正向元素，既不会作为历史种子，也不会参与该用户的共现贡献。数据库先对浏览事件按用户与作品计数，当前点赞、收藏和评分从各自状态表读取。前端页面不参与计算，避免客户端重试或本地缓存形成与服务端不同的信号口径。

### 4.2 物品相似度

对同一用户互动过的作品两两累计共现，将每个强度记为 x(u,i) = min(w(u,i),5)。设 n(u) 是该用户具有正向强度的作品数，活动惩罚项为 log₂(n(u)+1)。给定作品 i 和 j，使用下列式子估计相似度。

（4-2） co(i,j) = Σᵤ [x(u,i) × x(u,j) / log₂(n(u)+1)]

（4-3） sim(i,j) = co(i,j) / √[Σᵤ x(u,i)² × Σᵤ x(u,j)²]

分母用作品向量长度归一化，减少全局热门作品仅因交互次数多而获得较高相似度的倾向。分子对活跃用户做对数折减，使同一人访问很多作品时产生的大量两两共现不会得到相同强度的信号。未发生共同正向互动的作品对按零相似度处理，服务只保留存在共现的组合。按作品标识给组合键排序，可以用一个记录表示无向相似关系。

目标用户的协同分数由历史种子贡献相加。对每件候选作品 j，遍历其历史中的 i，在 i 与 j 不相同时，用该用户对 i 的行为强度乘以作品相似度，最后求和。这个分数表达了“与历史作品共同受到关注的程度”。高分可能来自一个相似度高的种子，也可能来自多个较弱但方向一致的种子。当前实现不对历史种子数再做归一化，不同用户的分值量级因此未必可比。系统只在单个用户的候选集中排序，暂不把该分数当作跨用户的绝对兴趣概率。

手算一组相似度可以检查实现。假定甲收藏作品 A，乙同时收藏 A 和 B，除此之外没有反馈。两人的收藏强度均为 3。A 的向量平方和为 18，B 为 9。唯一的共现来自乙，其正向作品数为 2，因此共现值为 9/log₂3，归一化相似度约为 0.446。甲对 B 的协同原分约为 3×0.446，即 1.339。另一个作品 C 如果从未与 A 共现，即使题材相近，其协同分仍为 0；题材相似可以在标签部分获得分数。手算只验证机制，样例数字不代表实际人群的行为分布。

### 4.3 标签亲和度

对每个标签 t 建立用户亲和度 a(u,t)。若用户明确选择某风格标签，该标签先得到 1。随后遍历用户的正向历史，把每件作品的标签贡献相加。对风格标签使用系数 0.6，对题材、媒介和年代使用系数 0.2，并将该作品的贡献乘以 min(w(u,i),3)/3。这样，收藏一次就可以达到单件作品对同一标签的上限，用户连续浏览不同作品则仍会产生累积效应。

（4-4） a(u,t) = E(u,t) + Σᵢ [I(t∈T(i)) × β(t) × min(w(u,i),3)/3]

其中 E 表示用户是否明确选择风格标签，T(i) 是作品的标签集合，β 为标签类别系数。一个候选作品的标签分为其所有标签亲和度之和再乘管理员配置的标签权重。该式使没有互动的新作品也能因标注准确获得分数。对于未选偏好但存在历史的用户，亲和度仍可由历史累积生成；对于无标签作品，标签分为零，但仍可能通过共同互动或热门得分进入结果。

当前求和方式可能使多标签作品取得较高分。若管理员对某类作品使用过细或重复的标注，排序就会反映标注密度而非兴趣强度。改善办法包括制定标签使用规范、避免同义标签重复、对每个维度分开归一化，或者在评估时比较标签数量不同的作品获得的曝光。现阶段保持直接求和便于检查得分来源，标签标注策略仍是系统质量的一部分。

### 4.4 混合排序和冷启动

记管理员设置的标签权重为 α，物品协同权重为 γ，默认值分别为 3 和 2。P(j) 表示作品热度，B(j) 表示是否置顶。热度使用当前有效状态，浏览每次贡献 0.25、每用户每件作品最多计 3 次，点赞贡献 2，收藏贡献 3，评分高于 3 时累加超出部分。该热度的浏览系数与用户画像中的 0.2 不同，应在分析时分别记录。

（4-5） S(u,j) = α × Σₜ∈T(j) a(u,t) + γ × Σᵢ≠ⱼ w(u,i) × sim(i,j) + 0.2 × ln(1+P(j)) + 2 × B(j)

热度在混合分中使用对数，避免互动总数的大幅增加线性推高排序。置顶作为固定加分进入个人排序，在热门入口则作为首要排序键。个人候选先按是否已在正向历史中分组，将未互动作品放在前面，再按得分、创建时间和作品标识降序排序。历史组可在候选不足时补充结果，明确低评分作品仍被排除。这个规则比直接按分数排序更强调发现新作品，也让用户可通过收藏夹单独回访已喜欢的作品。

[[REC]]

没有公开作品时返回空列表。选择最新时按创建时间和标识返回，不需要读取行为数据。选择热门或访客进入个人入口时，按置顶、热度、时间、标识排序。登录后若既无显式偏好也无正向历史，则沿用热门回退并排除其低评分作品；只有显式偏好时采用标签排序；存在正向历史时进入混合排序。算法输出策略字段和单条理由。理由优先展示主要分量能够支持的解释，例如协同分较高时提示共同欣赏，显式偏好命中时提示偏好风格。理由用于解释相对排序信号，无法证明两个用户具有相同审美。

### 4.5 排序案例与参数影响

沿用上文的 A、B 手算例，并假设 B 与 A 共享甲所选的风格，C 没有该风格且被管理员置顶。甲收藏 A 后，该风格亲和度由显式选择的 1 和 A 历史贡献的 0.6 构成。若 B 只有这一个标签，其标签分是 3×1.6 = 4.8，协同分约为 2×1.339 = 2.678。乙收藏 B 使其热度为 3，对数热度贡献约为 0.277，B 总分约为 7.755。若 C 无热度、无匹配标签且无共现，只有置顶贡献 2。B 排在 C 之前。A 因属于历史组排在两个未互动作品之后。

取消收藏或修改权重可改变相对位置。若甲取消对 A 的收藏且没有其他行为，甲仅剩显式风格偏好，策略会切换为偏好排序。若管理员把 α 与 γ 同时设置为 0，混合分中只剩热度与置顶，用户分组仍然有效，低评分作品也仍然排除。因此，把两个权重都设为 0 与直接调用热门接口存在区别。做消融实验时应该明确比较哪种入口，不能只看两个参数值便认为候选集和分组也一致。

### 4.6 计算开销与局限

设公开作品数为 M，行为矩阵非零元素数为 N，目标用户历史作品数为 H。构建行为矩阵大致随读取记录量和非零元素数增加。相似度计算需为每个用户处理其历史作品的组合，组合数量为 n(u)(n(u)−1)/2。对所有公开候选计算协同分，直接实现约需 M×H 次查询或累加。最终排序约需 M log M 的比较。很长的个别历史可在相似度阶段占据较多时间，活动惩罚只折减数值，无法减少组合数量。

面向较大目录，可以用离线任务保存每件作品的前 K 个邻居，在线只从目标用户的历史邻居和标签索引构建候选，热门列表以较短周期更新。这样会引入更新时间和状态一致性问题，例如撤销收藏后需要清理过时特征，下架作品应在接口返回前再过滤。原型保持按请求计算，以较低的部署复杂度换取即时反馈。生产化改造需要先测量主要耗时，再决定将哪些计算移出请求路径。

### 4.7 不同用户阶段的推荐行为

以首次进入发现页的访客为例，系统不拥有可信的个人历史，先展示置顶和热度靠前的作品。访客可以从作品详情看到风格、题材等信息，并决定是否注册。完成注册并选中偏好风格之后，即使未产生任何互动，也能因显式风格匹配看到不同的列表。此时未选中的风格并不表示排斥，置顶和热门仍可补充候选，以便用户接触偏好词表之外的作品。

当用户开始浏览和收藏，历史作品逐步提供标签与共现信号。假如其明确选择国风，但最近收藏了多件版画，排序可能同时出现国风和与版画题材相近的作品。是否发生这种变化，取决于权重和共同互动强度。历史信号主要按内容积累，原型没有时间衰减，所以很早的收藏依旧可能影响排序。对于审美兴趣会变化的用户，可通过加入时间权重缩短旧互动的影响周期，或提供暂时关闭历史个性化的入口。

新作品的协同项通常为零，即使使用热门也难以迅速积累行为。新作品发布后，只要已有标签与用户偏好吻合，就能通过标签项获得机会。最新入口则独立保障按创建顺序查看作品。若进一步引入探索曝光，需要说明将多少位置用于尚未充分展示的作品，记录展示后的停留、收藏与评分，并控制同一作品的重复展示频率。这样才能比较探索策略是否增加目录覆盖，或者仅将原本相关的结果移出了前列。

## 第5章 系统功能实现

### 5.1 启动与账号权限

应用工厂加载配置并初始化数据库扩展，注册业务蓝图，运行环境可使用 SQLite 文件或通过 PyMySQL 连接 MySQL。开发脚本分为初始化与运行两类，初始化在当前工作树内建立独立依赖环境，并在配置缺失时生成随机会话密钥。启动时前端代理转发 /api 请求。多个工作树同时启动可分别指定端口，避免在一个浏览器端口误访问其他分支的进程。启动脚本的实现位于环境分支，基线也保留逐条命令的运行方式。

注册接受用户名和密码，服务端校验长度并依赖数据库唯一约束防止重复账号。密码经 Werkzeug 摘要处理后存储。登录成功后重建会话，保存用户标识；登录失败统一提示凭据或状态问题。对后续请求，服务端重新读取用户状态和角色。资料修改由当前用户发起，修改密码时还需验证当前密码。管理员重置密码通过独立的受保护接口执行。前端通过会话状态显示不同入口，但角色访问条件始终由后端执行。

### 5.2 作品管理和图像处理

作品管理页通过表格展示作品条目，按名称与状态查询，并可编辑作品资料。提交数据前界面提供表单约束，后端仍重新验证。作品状态可在草稿、公开和下架之间转换。作品标签输入采用已存在的标签标识，避免同一作品表中混入临时类别字符串。作品发布时检查原图地址，外链应是带有效主机且不嵌入凭据的 HTTP(S) 地址，也可保存站内路径。限制 URL 形式可以阻止不合适的协议，但外部资源的版权与可用性仍需运营确认。

对本地上传，文件表单区分原图与封面。服务端检查扩展所对应的实际图像内容、大小与尺寸，再由 Pillow 解码处理。上传原图时保留供详情查看的文件并生成 WebP 封面，封面最长边控制在 1200 像素以内。独立封面上传可用于人工选择构图。单次上传上限为 10 MB，解码尺寸另设总像素与最长边边界。文件使用随机标识，资源接口为图片返回缓存时间。随着运营规模增长，需要为未保存表单或替换图片产生的孤立文件制定回收策略。

### 5.3 标签维护与作品检索

标签以类别和名称组合区分，可通过管理员页面统一创建、编辑和删除。用户偏好只能从风格类别中选择。标签从风格改为其他类别时，应移除其个人偏好引用；作品的分类关联仍可保留，以免修改类别意外删除作品内容。若删除标签，关联表的记录与偏好引用一起清理。数据库唯一约束和服务端校验共同减少重名和无效关联。

检索以公开作品为基础，再组合关键词与标签条件。关键词可作用于题名、作者等字段，作品分支对通配符做字面匹配处理，避免输入百分号时错误扩展查询。标签筛选核对传入标识是否属于指定类别。前端修改筛选条件时返回首屏，通过接口总数计算页数。在中小目录中，关系表联接足以完成查询；大目录可对热点筛选建立组合索引，也可在保留结构化筛选的同时使用独立全文索引。

### 5.4 互动与收藏夹

详情页读取服务端返回的当前点赞、收藏和评分，用户操作时发送期望状态，完成后再用响应更新显示。登录用户读取公开详情时记录浏览。对点赞和收藏，写入、删除和事件追加属于同一提交边界。相同状态的重复操作不会生成额外事件。评分只能使用整数；空值和布尔值需要拒绝，避免数据类型隐式转换。取消收藏后，用户可重新在详情页添加收藏，收藏列表以最新有效状态为准。

资料页保存个人资料与标签偏好，并展示收藏内容。状态变化应由服务器确认后反映在界面上。网络中断时，用户可以重新发起请求或刷新页面查询最终状态。前端的禁用与加载提示可减少重复点击，但后端仍需处理请求重放。当前设计通过复合键、状态检查与事务降低重复写入影响，并将相同请求重试作为验收用例。

### 5.5 推荐展示与后台配置

发现页允许在个性化、热门和最新三种模式之间切换。卡片展示封面、作品基本信息和推荐理由，并提供到详情页的入口。服务端提供明确的策略标识，页面可区分偏好驱动、历史驱动和热门回退。首次访问时，热门结果让用户先了解目录，登录并完成偏好选择后再次请求即可得到个性化列表。没有公开作品时显示空状态，避免将无数据误认为请求异常。

管理员可在管理界面修改标签权重和协同权重。权重保存后影响后续请求。界面将配置响应转换为数字，便于数字输入组件保持正确状态。统计接口提供账号、作品、公开作品与浏览事件数量，用于检查操作是否写入系统。这些统计适合管理观察。若进行推荐效果比较，应另外记录候选曝光与交互时间，以便把访问次数、用户规模和列表位置的影响分离开。

### 5.6 前端请求与页面状态

页面加载目录时需区分初始加载、正常有结果、正常为空和请求失败四类状态。接口返回空集合时，说明当前查询条件没有可展示的公开作品，可以提示用户清除筛选。请求失败时，界面需要保留查询参数，并根据响应内容决定是否提示重新登录或稍后重试。两类状态分别处理，可以避免用户把错误误认为馆藏为空，也可避免管理员因短暂网络错误重复创建同一条记录。

筛选与分页应共享同一组查询条件。用户输入关键词或改变任一标签维度后，应从第一页重新请求；翻页时保留既有条件。显示总数时使用接口返回的符合条件记录数，而不是当前页数组的长度。发出多个查询后，较旧的慢响应有可能覆盖刚输入的新结果。后续前端可用请求取消或递增请求标识避免这种问题。原型的功能检查主要验证静态请求参数与响应，连续快速交互和延迟响应仍需独立的浏览器用例。

详情页显示的交互状态属于当前登录用户，应在登录、退出或用户变化后重新读取。对未登录用户的互动，可以提示先登录并保留当前作品路径。若用户在请求发出后离开页面，返回的状态不能更新到另一件作品上。后续可给页面请求加入作品标识校验。将当前用户、作品标识和互动状态一并作为界面状态处理，可让页面在路由跳转和账号切换时保持一致。

### 5.7 管理配置与数据保护

推荐权重为有限范围内的数值。在界面使用数字输入可减少无效值，服务端仍需再次验证，保存为配置记录后由推荐服务读取。推荐分支对缺失和无法解析的值使用默认配置。业务人员调整权重时可记录调整前后的数值、原因与待验证的场景，再对同一份固定数据比较排序。如果直接依据当天浏览量决定哪组权重更好，目录内容与曝光变化可能会混入判断。

后台统计只面向有权限的管理员。对于展示用数据，页面可使用分组计数，避免暴露单个用户完整的浏览轨迹。行为日志中的用户标识虽然不是姓名，仍可能与账号数据关联，导出测试数据时应使用脱敏标识。服务端密码采用摘要保存，会话密钥应来自环境配置。部署时应让数据库账号只拥有应用所需权限，限制数据库端口访问并定期备份。用户提出删除个人历史或关闭个性化时，需要进一步明确数据保留范围、删除后的推荐回退与审计要求。

## 第6章 测试与结果分析

### 6.1 验证目标与环境

测试以用户可观察到的行为为主。目录测试验证搜索条件、分页、公开状态和图像约束；账号测试验证身份建立、资料维护、禁用账号和普通用户权限；交互测试关注用户重复操作和撤销后保存的状态；推荐测试使用小规模受控关系，检查排序信号、回退条件及候选过滤。每条用例尽量建立自己的数据库并显式插入数据，减少依赖测试顺序。测试所用图像和账号是合成数据，不代表真实作品馆藏或实际用户。

运行环境为 Windows 与 Python 3.12.14。接口测试使用 Flask 测试客户端与 SQLite 临时库，既保留请求路由、会话和数据库查询，又能在不启动外部 HTTP 进程的情况下重复执行。使用 Git 归档分别导出各分支提交，调用同一 Python 虚拟环境运行单元测试发现命令。分支导出不包括本机配置和已有数据库。为避免误用现有用户与作品数据，所有新测试都在隔离目录或测试连接中运行。

自动化测试以实际状态或返回值为判定依据。例如，只检查收藏接口返回 200 无法判断是否正确删除关联，测试还要重新访问收藏夹，核对列表缺少该作品。推荐测试需要检查候选排序或策略字段。对无历史用户，看到有作品返回并不足以证明系统使用了标签排序，因为热门回退也可能返回相同列表。测试需设置两个信号相互竞争的候选，再检查顺序和策略是否与预期相符。

### 6.3 推荐计算耗时

性能探测针对推荐提交 83a4f2f 的 recommend 服务函数。两组规模分别为 200 件公开作品和 50 名用户，以及 1000 件公开作品和 200 名用户。使用 Python 标准库伪随机数生成器，固定种子为 23030102，每个账号从公开作品中无放回抽取 12 件作为当前收藏。所有账号启用，目标账号标识为 1。两组均无标签、点赞、评分和浏览数据，从而集中观察候选规模及收藏共现增长时的开销。默认参数保持不变，个人列表长度为 20。

每组建立内存 SQLite 库并提交初始数据。每次在独立应用上下文中先读取目标用户，再用 perf_counter 计时，范围从调用 recommend 到获得返回对象。先进行 3 次预热，再顺序执行 30 次，确认每次均返回 20 件作品并使用混合策略。P50 取样本中位数，P95 取升序后的第 29 个观测值。测试包含函数内的数据查询、信号聚合、相似度、排序和作品序列化，未计入用户查询、HTTP 协议处理、网络、浏览器和图像下载。

该实验表明，在指定的单机串行与合成数据条件下，推荐函数可完成计算并返回固定数量的结果。要判断实际并发能力，需要使用完整 HTTP 链路，在 MySQL 上执行不同目录规模、不同用户历史分布和并发等级的压测。应分别记录吞吐、响应延迟分位数、数据库查询耗时与错误率，并对比开启及关闭缓存后的差别。还应在真实图像资源上度量首屏传输字节和图像显示时间，这与推荐函数的响应成本是不同问题。

### 6.4 离线推荐评价方案

实际推荐质量应通过用户对后续作品的行为评价。可在取得有权使用的匿名数据后，为每条记录保存用户标识、作品标识、行为类型、时间与必要的曝光信息。先选定时间截点，用截点前的浏览和正向行为构建标签亲和度、协同关系和热度，再将截点后的收藏或高评分作为相关作品集合。每个测试用户只使用其当时可知的信息，候选限定在截点时可见的目录。对未登录访客、缺少历史的新用户和已有互动的用户分别统计，避免单个平均值掩盖不同使用场景。

设推荐列表长度为 K，H 表示命中的相关作品数，G 表示测试阶段相关作品数。Precision@K 取 H 除以 K，Recall@K 取 H 除以 G。当 G 为零时，该用户的 Recall@K 没有定义，可在总体结果中排除并报告排除数量。NDCG@K 对较高位置的命中给予较高权重，可用于比较相同命中数的不同排序。还可将所有用户的推荐列表去重后除以可推荐作品总数，得到目录覆盖率。风格维度的多样性可以用列表内作品风格标签的差异度量。指标只在相同候选集、时间切分、相关性定义和 K 下可直接比较[4,7-9]。

建议将热门、仅标签、仅 ItemCF 和混合作为对照方法，并固定对下架作品和低评分作品的处理。为了检验冷启动，另报告新作品和新用户的结果。若混合方法相关性提高但目录覆盖下降，需要比较各风格的曝光变化；若热门入口能在大部分访客中取得更多点击，也要区分高点击是否仅源于此前较多的曝光。使用受控数据验证规则有助于排除明显实现错误，但不能提供这些判断所需的证据。

### 6.5 合并和部署验收

各模块的分支测试使用同一共享基线。合并时应先确认作品分支的发布约束与其他测试的数据创建方式一致。例如，其他分支用例可能创建没有原图地址的公开测试作品，而作品模块在管理员接口中要求发布时提供合法原图。合并后需要更新测试数据契约并重新执行全集。推荐接口增加策略和理由字段，已有前端仍应能读取 items，新版前端则需在各回退场景下显示合理提示。交互模块的状态与推荐读取的状态表一致，仍需在合并后从实际浏览器做一次用户全过程验收。

部署验收依次建立独立的 MySQL 库与应用账号，配置生产会话密钥、HTTPS 入口和上传目录，执行建表或迁移，构建前端并通过反向代理提供页面。完整验收可让管理员发布一件有授权使用的作品，再让普通用户从筛选列表进入详情，产生浏览、收藏和评分，最后检查推荐和后台统计。应另行模拟文件丢失、数据库连接中断与无效会话，检查日志和错误提示。该部署和并发验证尚待在统一版本完成，不能用开发进程健康接口或函数耗时结果替代。

### 6.6 结果解释与威胁分析

受控测试的优势是可以事先确定期望。例如，仅用收藏状态和一个置顶候选就能检查权重变化是否改变顺序。它的不足是候选很少、行为分布由作者构造，无法代表真实用户的访问目的。真实数据中可能出现大量访客、少量多次访问用户、相似作品重复录入以及同一作者的集中曝光。对此应保存目录规模、标签缺失率、账号活跃度与候选覆盖情况，使读者能够判断实验外推的范围。

串行耗时对计算成本提供初步证据。随机均匀抽样不能复现热门作品被反复收藏的集中分布，也没有覆盖极长历史。更严格的性能实验可控制变量：先固定每个用户的正向作品数，逐步增加目录规模；再固定目录规模并改变历史长度；最后在相同数据上改变并发数量。数据初始化、预热和计时范围需要保持一致。对于数据库层，应记录执行计划、热点索引和查询数量。对于端到端链路，应说明浏览器缓存和图像是否命中，否则延迟无法归因。

离线推荐结果还可能受曝光偏差影响。历史上从未展示的作品难以获得正向互动，不能直接按负样本处理。若能记录曝光，可以将评价候选限定为当时可见的作品，并按显示位置和曝光次数分组。对于被用户反复收藏或长时间停留的作品，也不应仅用总点击判断满意度。后续可结合会话级发现率、收藏后回访以及用户自评，分别观察推荐相关性、可解释性与欣赏体验。该方案需要先完成数据采集与权限流程。

## 第7章 总结与展望

### 7.1 研究总结

本课题围绕美术作品目录中的探索需求设计系统。作品描述、结构化标签、浏览与互动组成可持续维护的数据基础；账号和权限把公众浏览、个性化数据及管理操作分开。前端使用 Vue 3 与 Element Plus 实现作品浏览和管理，Flask 提供接口，通过关系型数据库保存用户、标签、作品、行为及推荐配置。图像原图与封面分开，列表以封面降低加载开销，详情保留欣赏所需的图像入口。

混合推荐将标签和协同信号用于不同的信息条件。显式选择的风格帮助缺少历史的用户进入目录，浏览与有效交互增加画像，物品相似度补充跨用户的共同关注关系。热门和最新入口提供探索方式，低评分约束减少用户明确拒绝的作品再次出现。作品状态、互动撤销、账号启停和权重变化均可通过接口测试验证。受控测试与计算耗时探测支持对规则和演示规模的判断，推荐效果仍取决于真实作品标注与实际使用数据。

### 7.2 后续工作

近期工作是合并各功能分支，固定答辩版本并完成 MySQL、前端和浏览器整体验收。应统一测试数据的发布条件与推荐接口契约，记录真实截图、操作步骤和环境版本。对作品资料应保存合法来源与使用许可，核对作者及风格标签，并检查图像加载质量。若需要独立审核员，可补充审核角色、待审状态与审核事件，明确与管理员之间的职责。正式上线还要完善迁移、备份和访问防护。

算法方面可先构建有时间戳和曝光记录的反馈样本，比较不同权重的相关性、覆盖率和分组表现。需要将热门偏差、重复曝光和标签密度纳入诊断，同时保留用户对显式偏好的控制。数据量增加时，预计算稀疏物品邻居并缓存热门榜，再按作品状态和用户低评分做最终过滤。更新延迟、缓存失效和离线指标与用户真实体验之间的关系，需要结合部署数据继续验证。
